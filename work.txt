# Git & GitHub 정리

## 1. 과정 목표

Git과 GitHub를 활용해 코드를 안전하게 관리하고 협업할 수 있는 기본 역량을 갖춘다.

---

# 2. 버전 관리의 필요성

## 버전 관리(Version Control)란?

파일이나 코드의 **변경 이력을 체계적으로 기록하고 관리하는 것**이다.

* 언제, 누가, 무엇을 바꿨는지 확인할 수 있음
* 필요하면 과거 상태로 되돌릴 수 있음
* 변경 이력을 추적하고 실수를 복구할 수 있음
* 여러 사람이 충돌을 줄이며 협업할 수 있음

### Git을 사용하는 이유

파일을 복사해서 관리하면:

* `final.py`, `final_v2.py`, `진짜최종.py`처럼 파일이 계속 늘어남
* 변경 이유와 내용이 남지 않음
* 협업 시 어떤 파일이 최신인지 알기 어려움

Git을 사용하면:

* 변경 내용이 **커밋 단위**로 기록됨
* 특정 시점으로 되돌릴 수 있음
* 여러 사람이 동시에 작업 가능
* 변경 이력과 책임이 명확함

---

# 3. Git vs GitHub

## Git

* 버전 관리를 위한 도구(프로그램)
* 내 컴퓨터에서 동작
* 버전 관리 엔진 역할

## GitHub

* Git 저장소를 올려두는 웹 서비스
* 코드 공유 및 협업 플랫폼
* Pull Request, Issue, Review 등의 기능 제공

> **Git = 버전 관리 엔진**
> **GitHub = 협업과 공유를 위한 서비스**

---

# 4. Git 기본 개념

## Repository(레포지토리)

파일과 그 변경 이력을 함께 관리하는 저장소이다.

프로젝트 전체와 모든 버전 기록이 들어 있다.

### 로컬 저장소

내 컴퓨터에 있는 저장소

```bash
git init
```

프로젝트 폴더에서 `git init`을 실행하면 해당 폴더가 Git Repository가 된다.

### 원격 저장소

GitHub와 같은 서버에 있는 저장소

```bash
git clone 저장소_URL
```

GitHub에서 Repository를 생성한 후 `git clone`으로 내 컴퓨터에 복사할 수 있다.

---

## Commit(커밋)

변경 사항을 하나의 기록으로 저장하는 단위이며, 하나의 버전이라고 볼 수 있다.

* 무엇을 왜 바꿨는지 메시지로 남김
* 특정 시점의 프로젝트 상태를 저장
* 과거로 되돌아갈 수 있는 기준점 역할

```bash
git commit -m "회원가입 기능 추가"
```

---

## Branch(브랜치)

독립적으로 작업할 수 있는 작업 공간이다.

* 기존 코드를 건드리지 않고 기능 개발 가능
* 여러 기능을 동시에 개발할 수 있음
* 작업이 끝나면 `merge`를 통해 병합

```bash
git branch feature/login
git switch feature/login
```

---

## HEAD

현재 내가 작업 중인 위치를 가리키는 포인터이다.

일반적으로 현재 브랜치의 최신 커밋을 가리킨다.

> HEAD가 움직인다는 것은 작업의 기준이 바뀐다는 의미이다.

---

## Working Directory

실제로 파일을 수정하고 작업하는 공간이다.

아직 Git에 기록되지 않은 변경 사항이 있을 수 있다.

---

## Staging Area

다음 커밋에 포함할 변경 사항을 미리 모아두는 공간이다.

```text
Working Directory
        ↓ git add
Staging Area
        ↓ git commit
Repository
```

# 8. 로컬에서 Git 사용하기

## ① Git Repository 초기화

현재 폴더를 Git Repository로 초기화한다.

```bash
git init
```

실행하면 `.git` 폴더가 생성되고 해당 폴더에서 버전 관리가 시작된다.

---

## ② 현재 상태 확인

```bash
git status
```

현재 Repository의 상태를 확인한다.

확인할 수 있는 내용:

* 수정된 파일
* Staging 여부
* 커밋 가능한 변경 사항

---

## ③ Staging

변경된 파일을 Staging Area로 올린다.

```bash
git add 파일명
```

또는

```bash
git add .
```

`git add`는 커밋에 포함할 변경 사항을 선택하는 단계이다.

> `git add`를 했다고 해서 아직 커밋이 생성된 것은 아니다.

---

## ④ Commit

Staging Area의 변경 사항을 하나의 버전으로 기록한다.

```bash
git commit -m "커밋 메시지"
```

커밋은 나중에 되돌아갈 수 있는 기준점 역할을 한다.

# 9. 커밋 메시지 작성 규칙

좋은 커밋 메시지는 **무엇을 했는지 한눈에 알 수 있어야 한다.**

### 권장 규칙

* 명확하고 간결하게 작성
* 동사로 시작
* 한 커밋 = 한 작업

### 예시

```text
Add login API
Fix password validation bug
Refactor user service
```

# 10. .gitignore

`.gitignore`는 Git 버전 관리에서 **제외할 파일을 지정하는 설정 파일**이다.

불필요하거나 민감할 수 있는 파일이 커밋되는 것을 방지한다.

### 일반적으로 제외하는 파일

* 환경 변수 파일
* 빌드 결과물
* 개인 설정 파일
* 로그 파일

### 예시

```gitignore
.env
__pycache__/
*.log
```

### 주의

이미 커밋된 파일은 `.gitignore`에 추가해도 Git이 계속 추적한다.

이 경우:

```bash
git rm --cached 파일명
```

# 11. 브랜치 이해하기

브랜치는 기존 작업과 분리된 **독립적인 작업 흐름**이다.

* 기능 개발
* 실험
* 수정 작업

등을 안전하게 진행할 수 있다.

협업과 안정적인 배포를 위해서는 브랜치를 잘 관리하는 것이 중요하다.

### 주요 명령어

브랜치 목록 확인:

```bash
git branch
```

브랜치 생성:

```bash
git branch feature/ui
```

브랜치 전환:

```bash
git switch feature/ui
```

---

# 12. 브랜치 관리 전략

어떻게 브랜치를 나누고 합칠지에 대한 약속이다.

대표적인 구조:

```text
main
 └── dev
      ├── feature/*
      └── hotfix/*
```

### 주요 브랜치

| 브랜치         | 용도                 |
| ----------- | ------------------ |
| `main`      | 배포 가능한 안정 버전       |
| `dev`       | 개발 중인 기능을 테스트하는 버전 |
| `feature/*` | 기능 개발              |
| `hotfix/*`  | 긴급 수정              |

# 13. 브랜치 병합

## git merge

다른 브랜치의 작업 내용을 현재 브랜치로 합치는 명령어이다.

```bash
git merge feature/ui
```

---

## Fast-forward merge

브랜치가 직선으로 이어지는 경우이다.

별도의 병합 커밋을 만들지 않고 커밋 포인터만 이동한다.

```text
main
  ↓
  1 ── 2 ── 3
             ↑
          feature
```

---

## 3-way merge

브랜치가 갈라졌다가 다시 합쳐지는 경우이다.

이 경우 병합 커밋이 생성된다.

> **분기가 없으면 Fast-forward**
> **분기가 있으면 3-way merge**

---

# 14. Merge Conflict

같은 파일의 같은 부분을 서로 다르게 수정하면 충돌(Conflict)이 발생한다.

Git은 먼저 자동 병합을 시도하고, 판단이 필요한 경우에만 충돌을 알려준다.

## 충돌 해결 과정

1. 충돌 파일 확인
2. 충돌 코드 직접 수정
3. 새로운 커밋 생성

예시:

```bash
git merge feature
```

충돌 내용을 확인:

```bash
cat test.txt
```

파일 수정:

```bash
vi test.txt
```

수정 후 커밋:

```bash
git commit -am "resolve merge conflict"
```

커밋 그래프 확인:

```bash
git log --oneline --graph
```

# 15. GitHub 기초

GitHub에 있는 Git Repository이다.

원격 저장소는:

* 여러 사람이 같은 코드를 공유

```bash
git remote add origin 원격주소
```

원격 저장소 확인:

```bash
git remote -v
```

# 16. git push / git pull

로컬 Repository와 원격 Repository를 동기화하는 명령어이다.

## git push

로컬의 커밋을 원격 Repository로 올린다.

```bash
git push -u origin main
```

## git pull

원격 Repository의 변경 사항을 내려받아 로컬에 반영한다.

```bash
git pull
```

### 기본 흐름

```text
로컬 작업
   ↓
git add
   ↓
git commit
   ↓
git push
   ↓
GitHub
```

반대로 GitHub의 변경 사항을 가져올 때:

```text
GitHub
   ↓
git pull
   ↓
로컬 Repository
```

# 17. Clone vs Fork

## Clone

원격 Repository를 그대로 내 컴퓨터로 복사한다.

```bash
git clone 저장소_URL
```

* 같은 Repository에 push 권한이 있을 때 사용
* 팀 내부 협업에 주로 사용

## Fork

다른 사람의 Repository를 내 GitHub 계정으로 복사한다.

* 원본 Repository에 직접 push 권한이 없을 때 사용
* 오픈소스 기여 방식으로 주로 사용

---

# 18. Pull Request

변경 사항을 원본 Repository에 반영해달라고 요청하는 것이다.

Pull Request에서는:

* 변경 내용 설명
* 리뷰 요청
* 병합 전 검증

등을 진행한다.

```text
내 브랜치
   ↓
Push
   ↓
Pull Request
   ↓
Code Review
   ↓
Merge
```

---

* 코드 중심으로 리뷰
* 이유를 남긴 코멘트
* 승인 후 병합

# 21. 협업 실습 — Fork & Clone

Fork 방식으로 오픈소스에 기여할 때의 기본 흐름이다.

### 1. Issue 생성

작업할 Issue를 생성한다.

### 2. Fork

내 GitHub 계정으로 Repository를 Fork한다.

### 3. Clone

Fork한 Repository를 로컬로 가져온다.

```bash
git clone 내_포크_저장소_URL
```

### 4. 원본 저장소 연결

```bash
git remote add upstream 원본_저장소_URL
```

### 5. 최신 코드 받기

```bash
git pull upstream main
```

### 6. 브랜치 생성

```bash
git switch -c feature/add-my-name
```

이후 작업 → Commit → Push → Pull Request 순서로 진행한다.

# 23. 자주 사용하는 명령어

## git show

특정 커밋 하나를 집중해서 살펴볼 때 사용한다.

확인할 수 있는 내용:

* 해당 커밋의 변경 내용(diff)
* 커밋 메시지
* 작성자
* 날짜

```bash
git show
```

현재 브랜치의 최신 커밋을 확인:

```bash
git show HEAD
```

특정 커밋 확인:

```bash
git show 커밋해시
```

---

## git diff

두 상태 간의 차이점을 비교한다.

### Working Directory ↔ Staging Area

```bash
git diff
```

### Staging Area ↔ HEAD

```bash
git diff --staged
```

### 커밋 ↔ 커밋

```bash
git diff HEAD~1 HEAD
```

주요 활용:

* 커밋 전 변경 사항 점검
* 병합·충돌 원인 분석

---

## git blame

파일의 각 줄이 **누가, 언제, 어떤 커밋에서 수정됐는지** 추적한다.

```bash
git blame main.py
```

버그 원인을 추적하거나 특정 코드가 왜 작성되었는지 확인할 때 활용할 수 있다.

---

## git stash

현재 작업 중인 변경 사항을 임시로 저장한다.

커밋하지 않고 작업을 잠시 중단해야 할 때 유용하다.

### 현재 변경 사항 임시 저장

```bash
git stash
```

### stash 목록 확인

```bash
git stash list
```

### 가장 최근 stash 적용 후 삭제

```bash
git stash pop
```

### stash를 삭제하지 않고 적용

```bash
git stash apply
```

특정 stash를 적용할 수도 있다.

# 24. git reset

브랜치의 기준을 과거 커밋으로 이동시키는 명령어이다.

> **히스토리를 변경하기 때문에 사용에 주의해야 한다.**

### --soft

커밋만 취소하고 변경 내용은 유지한다.

```bash
git reset --soft HEAD~1
```

### --mixed

커밋과 Staging을 취소한다.

기본 옵션이다.

```bash
git reset --mixed HEAD~1
```

### --hard

커밋, Staging, 파일의 변경 내용까지 모두 되돌린다.

```bash
git reset --hard HEAD~1
```

> `--hard`는 변경 내용이 삭제될 수 있으므로 특히 주의한다.

또한 협업 중인 브랜치에서 `reset`을 사용할 때는 주의해야 한다.

# 25. git revert

특정 커밋을 되돌리는 **새로운 커밋을 생성**한다.

```bash
git revert 커밋해시
```

특징:

* 기존 기록은 그대로 유지
* 해당 커밋을 취소했다는 기록이 남음
* 협업 중 안전하게 롤백할 때 유용

### reset과의 차이

| 명령어          | 특징                      |
| ------------ | ----------------------- |
| `git reset`  | 과거로 이동하며 히스토리를 변경       |
| `git revert` | 기존 히스토리를 유지하고 취소 커밋을 생성 |

# 26. git commit --amend

마지막 커밋을 수정하는 명령어이다.

```bash
git commit --amend
```

가능한 작업:

* 최근 커밋 수정
* 커밋 메시지 수정
* 변경 파일 추가/제거

기존 커밋 메시지를 그대로 유지하려면:

```bash
git commit --amend --no-edit
```

# 27. 전체 Git 기본 흐름

Git을 처음 사용할 때 가장 중요한 흐름은 다음과 같다.

```text
① 프로젝트 폴더 이동
        ↓
② git init
        ↓
③ 파일 작성 / 수정
        ↓
④ git status
        ↓
⑤ git add
        ↓
⑥ git commit
        ↓
⑦ git remote add origin
        ↓
⑧ git push
```

협업에서는 브랜치를 추가한다.

```text
main
 │
 ├── feature/login
 │       ↓
 │    작업
 │       ↓
 │    commit
 │       ↓
 │    push
 │       ↓
 │   Pull Request
 │       ↓
 │  Code Review
 │       ↓
 └──── merge
```

# 29. 핵심 개념 정리

### Git의 기본 구조

```text
Working Directory
       │
       │ git add
       ↓
Staging Area
       │
       │ git commit
       ↓
Local Repository
       │
       │ git push
       ↓
Remote Repository(GitHub)
```

### 협업의 기본 구조

```text
Repository
    ↓
Branch 생성
    ↓
작업
    ↓
Commit
    ↓
Push
    ↓
Pull Request
    ↓
Code Review
    ↓
Merge
```

### 꼭 기억할 개념

* **Git** → 버전 관리 도구
* **GitHub** → Git Repository를 기반으로 한 공유·협업 서비스
* **Repository** → 프로젝트와 변경 이력을 저장하는 공간
* **Commit** → 변경 사항을 기록하는 하나의 버전
* **Branch** → 독립적인 작업 공간
* **HEAD** → 현재 작업 기준을 가리키는 포인터
* **Working Directory** → 실제로 작업하는 공간
* **Staging Area** → 다음 커밋에 포함할 변경 사항을 모아두는 공간
* **Push** → 로컬의 변경 사항을 원격으로 업로드
* **Pull** → 원격의 변경 사항을 로컬로 가져옴
* **Pull Request** → 변경 사항을 원본에 반영해달라고 요청
* **Merge** → 브랜치의 작업 내용을 합침
* **Reset** → 과거 상태로 기준을 이동
* **Revert** → 기존 기록을 유지하면서 취소 커밋 생성
